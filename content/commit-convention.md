# 커밋 컨벤션

커밋 메시지 규칙을 왜 맞추는지부터 짚고 간다. 예쁘게 보이려고 하는 게 아니다. 세 가지 실익이 있다.

- **찾을 수 있다.** 3개월 뒤 "카드 만료일 검증 언제 바뀌었지"를 `git log --grep` 한 줄로 찾는다.
- **자동화가 붙는다.** 릴리즈 노트, 버전 올리기, 변경 이력이 커밋 메시지에서 그대로 나온다.
- **리뷰가 빨라진다.** 타입만 보고도 이 커밋이 동작을 바꾸는지 아닌지 판단할 수 있다.

기준은 Conventional Commits다. 형식은 이렇다.

```
<타입>(<스코프>): <제목>

<본문>

<꼬리말>
```

제목 줄은 50자 안쪽, 마침표 없이, 명령형 또는 명사형으로 끝낸다. 본문은 72자에서 줄바꿈한다. 본문과 꼬리말은 빈 줄로 띄운다.

---

## 타입 11개

### feat — 기능 추가

사용자나 다른 시스템이 **새로 할 수 있게 된 일**이 있을 때 쓴다. 판단 기준은 "이 커밋 전에는 불가능했던 게 가능해졌는가"다.

```
feat(payment): 카드 만료일 검증 추가
feat(refund): 부분 환불 API 엔드포인트 추가
feat(auth): 결제 요청에 멱등성 키 헤더 지원
```

**옆 타입과의 경계** — `fix`와 붙는다. 없던 걸 만들면 feat, 있는데 잘못 도는 걸 바로잡으면 fix다. "요구사항에 있었는데 구현이 안 돼 있었다"면 fix가 아니라 feat다. 티켓이 버그로 잡혀 있어도 마찬가지다. 티켓 종류가 아니라 코드가 기준이다.

### fix — 버그 수정

**있어야 할 동작이 안 되고 있던 걸** 바로잡는다. 기준은 "고치기 전 동작이 명세와 어긋났는가"다.

```
fix(payment): 만료월이 12일 때 검증이 통과하던 문제 수정
fix(refund): 환불 금액이 0원이면 500 대신 400 반환
fix(webhook): 재시도 시 중복 결제 승인되던 문제 수정
```

**옆 타입과의 경계** — `feat`와 붙는다. 위를 참고한다. 그리고 "버그는 아닌데 코드가 이상해서 고쳤다"면 fix가 아니라 `refactor`다. 사용자가 겪은 증상이 없으면 fix가 아니다.

### docs — 문서

코드가 아니라 **읽는 것**만 바뀐 경우다. README, 주석, API 문서, ADR, 이 교재 같은 것.

```
docs(readme): 로컬 개발 환경 구성 절차 추가
docs(payment): 결제 상태 전이 다이어그램 갱신
docs: 커밋 컨벤션 문서에 revert 타입 추가
```

**옆 타입과의 경계** — 주석만 고쳤으면 docs다. 그런데 주석을 고치면서 변수 이름도 바꿨다면 그건 `refactor`다. 한 커밋에 섞이면 타입을 못 정한다는 뜻이고, 그건 커밋을 쪼개라는 신호다. JSDoc 같은 코드 안 문서도 docs로 본다.

### style — 코드 모양

**동작이 1비트도 안 바뀌는** 포맷 변경이다. 공백, 들여쓰기, 세미콜론, import 정렬, 줄바꿈, 포매터 적용.

```
style: prettier 3.x 적용에 따른 전체 포맷 정리
style(payment): import 순서 정리
style(refund): 4칸 들여쓰기로 통일
```

**옆 타입과의 경계** — `refactor`와 붙는다. 아래 "헷갈리는 쌍"에서 따로 다룬다. 한 줄 요약하면, **AST가 그대로면 style, AST가 바뀌면 refactor다.** CSS를 고친 건 style이 아니라 feat이나 fix다. 화면이 달라지니까.

### refactor — 구조 변경

**겉에서 본 동작은 같은데 안이 달라진 것.** 이름 바꾸기, 함수 쪼개기, 중복 제거, 조건문 정리, 의존성 방향 바꾸기.

```
refactor(payment): PaymentValidator를 규칙별 클래스로 분리
refactor(refund): 중복된 금액 계산 로직을 공통 함수로 추출
refactor(order): 주문 상태 판별을 if 체인에서 맵 조회로 교체
```

**옆 타입과의 경계** — `perf`, `style`, `fix` 셋 다와 붙는다. 빨라졌으면 perf, 모양만 바뀌었으면 style, 동작이 달라졌으면 refactor가 아니다. 리팩터링 중에 버그를 발견했다면 커밋을 나눠라. 리팩터 커밋과 fix 커밋은 별개여야 나중에 되돌릴 수 있다.

### perf — 성능 개선

**동작은 같고 더 빠르거나 덜 먹는 것.** 숫자로 말할 수 있어야 한다.

```
perf(payment): 결제 내역 조회에 복합 인덱스 추가로 p95 1.8s → 210ms
perf(refund): N+1 쿼리 제거로 환불 목록 조회 쿼리 42회 → 3회
perf(webhook): 페이로드 직렬화를 스트리밍으로 바꿔 메모리 절반으로 감소
```

**옆 타입과의 경계** — `refactor`와 붙는다. 의도가 성능이고 결과가 측정됐으면 perf, 아니면 refactor다. 측정 숫자가 없으면 perf라고 부를 근거가 없다고 보는 팀이 많다. 본문에 before/after를 적어두면 논쟁이 사라진다.

### test — 테스트

**테스트 코드만** 건드린 경우다. 추가, 수정, 삭제, 픽스처, 테스트 유틸 전부 포함한다.

```
test(payment): 만료일 경계값 테스트 케이스 추가
test(refund): 부분 환불 통합 테스트 추가
test: 결제 픽스처를 빌더 패턴으로 교체
```

**옆 타입과의 경계** — 프로덕션 코드를 고치면서 테스트도 같이 고쳤다면 그건 `feat`나 `fix`다. test는 테스트만 건드릴 때 쓴다. TDD로 작업한다면 테스트 먼저 커밋(test), 구현 커밋(feat) 순서로 나누는 팀도 있고, 한 커밋으로 묶는 팀도 있다. 팀 규칙으로 정해두면 된다.

### build — 빌드와 의존성

**빌드 결과물이나 의존성이 달라지는 것.** 패키지 추가·삭제·버전 업, 번들러 설정, tsconfig, Dockerfile, 빌드 스크립트.

```
build: isomorphic-git 1.42로 업그레이드
build: vite 설정에 경로 별칭 추가
build(docker): 베이스 이미지를 node:22-alpine으로 변경
```

**옆 타입과의 경계** — `ci`, `chore`와 붙는다. 아래 "헷갈리는 쌍"에서 다룬다. 한 줄로는, **빌드 산출물에 영향이 있으면 build다.**

### ci — CI 설정

**CI/CD 파이프라인 설정**만 건드린 경우다. 워크플로 파일, 러너 설정, 배포 스크립트, 캐시 설정.

```
ci: MR 파이프라인에 타입 체크 잡 추가
ci: 테스트 잡을 매트릭스로 바꿔 node 20/22 동시 실행
ci(deploy): 스테이징 배포를 main 머지 시점으로 이동
```

**옆 타입과의 경계** — `build`와 붙는다. 내 노트북에서 `npm run build`가 달라지면 build, CI에서만 달라지면 ci다. Dockerfile은 애매한데, 빌드에 쓰이면 build, 배포 파이프라인 전용이면 ci로 본다. 팀에서 한 번 정하고 가면 된다.

### chore — 나머지 잡일

**위 어느 것도 아닌 유지보수 작업.** `.gitignore` 수정, 라이선스 파일, 에디터 설정, 죽은 파일 삭제, 자동 생성 파일 갱신.

```
chore: .gitignore에 .env.local 추가
chore: 사용하지 않는 레거시 결제 어댑터 삭제
chore: CODEOWNERS에 결제팀 추가
```

**옆 타입과의 경계** — chore는 **마지막에 고르는 타입**이다. "딱히 안 떠올라서 chore" 하는 순간 chore가 전체 커밋의 절반이 된다. 의존성은 build, 파이프라인은 ci, 문서는 docs로 먼저 밀어내고 남는 것만 chore다.

### revert — 되돌리기

**이미 들어간 커밋을 취소**하는 커밋이다. `git revert`가 메시지를 자동으로 만들어주는데, 형식만 컨벤션에 맞춘다.

```
revert: feat(payment): 카드 만료일 검증 추가

This reverts commit 3f9a2c1e.
되돌린 이유: 해외 카드 일부가 만료월을 0-based로 보내와 정상 결제가 막힘. PAY-247에서 다시 올립니다.
```

```
revert: perf(refund): 환불 목록 조회에 캐시 적용

This reverts commit 8b41d02.
되돌린 이유: 캐시 무효화 누락으로 취소된 환불이 목록에 계속 남음.
```

```
revert: build: node 22로 런타임 업그레이드

This reverts commit c17e5aa.
되돌린 이유: 결제 게이트웨이 SDK가 22에서 TLS 핸드셰이크에 실패.
```

**옆 타입과의 경계** — 되돌리는 게 아니라 **고치는** 거라면 fix다. 리버트는 "그 커밋이 없었던 상태로" 만드는 것이고, 새 코드를 얹어 증상을 없애면 fix다. 그리고 **반드시 되돌린 이유를 본문에 적는다.** 이유 없는 리버트는 나중에 그 기능을 다시 넣을 때 같은 함정에 그대로 빠진다.

## 헷갈리는 쌍 네 가지

### feat vs fix — 새로 생긴 건가, 고친 건가

질문 하나로 갈린다. **"이 커밋 직전 상태가 버그인가?"**

| 상황 | 타입 | 왜 |
| --- | --- | --- |
| 환불 API에 부분 환불을 새로 넣음 | feat | 전에는 전액 환불만 됐고, 그건 버그가 아니라 미구현이었다 |
| 부분 환불이 소수점에서 1원씩 깎이던 걸 고침 | fix | 직전 상태가 명세 위반이다 |
| 명세에 있었는데 아예 구현이 빠져 있던 검증 추가 | feat | 코드가 없었으니 없던 기능이다. 티켓이 버그로 잡혀 있어도 feat다 |
| 검증은 있는데 조건이 잘못돼서 통과되던 걸 고침 | fix | 코드는 있었고 결과가 틀렸다 |

경계에서 다투게 되면 **릴리즈 노트에 뭐라고 쓸지**를 생각해보면 된다. "이제 부분 환불이 됩니다"면 feat, "부분 환불 금액이 정확해졌습니다"면 fix다.

### refactor vs perf — 같은가, 빨라졌는가

둘 다 겉보기 동작은 안 바뀐다. 갈림길은 **의도와 측정**이다.

| 상황 | 타입 |
| --- | --- |
| 200줄짜리 함수를 5개로 쪼갬. 속도는 그대로 | refactor |
| 루프 안 쿼리를 밖으로 빼서 N+1 제거. 코드도 짧아짐 | perf |
| 캐시를 넣어 조회가 8배 빨라짐. 코드는 오히려 복잡해짐 | perf |
| 알고리즘을 O(n²)에서 O(n log n)으로 바꿈 | perf |
| 이름을 바꾸고 타입을 붙였더니 우연히 조금 빨라짐 | refactor |

마지막 줄이 핵심이다. **우연히 빨라진 건 perf가 아니다.** perf는 "빠르게 하려고 했고, 얼마나 빨라졌는지 안다"는 주장이다. 주장에는 근거가 붙어야 한다. 본문에 숫자를 적어라.

### style vs refactor — 파서가 다르게 읽는가

기계적인 기준이 하나 있다. **코드를 파싱한 결과(AST)가 달라지면 refactor, 그대로면 style이다.**

| 변경 | 타입 |
| --- | --- |
| 들여쓰기 탭 → 스페이스 | style |
| 세미콜론 일괄 추가 | style |
| import 순서 정렬 | style |
| 줄 길이 맞춰 줄바꿈 | style |
| 변수 이름 `d` → `expiryDate` | refactor |
| `if` 중첩을 얼리 리턴으로 변경 | refactor |
| 익명 함수를 화살표 함수로 변경 | refactor |
| `let`을 `const`로 변경 | refactor |

마지막 두 줄이 자주 다툰다. 겉보기엔 스타일 같지만 코드의 의미가 달라진다(`this` 바인딩, 재할당 가능 여부). 확신이 안 서면 refactor로 보내라. **style은 "리뷰어가 안 읽어도 되는 커밋"이어야 한다.** 조금이라도 읽어봐야 한다면 style이 아니다.

### chore vs build vs ci — 어디에 영향을 주는가

셋 다 프로덕션 코드가 아니라서 뭉뚱그려지기 쉽다. 영향 범위로 가른다.

| 질문 | 예 | 타입 |
| --- | --- | --- |
| `npm run build` 결과물이 달라지나? | 패키지 버전 업, vite 설정, tsconfig | build |
| CI 파이프라인에서만 달라지나? | 워크플로 파일, 캐시 키, 배포 스텝 | ci |
| 둘 다 아닌가? | `.gitignore`, `.editorconfig`, CODEOWNERS | chore |

구체적으로 자주 나오는 것들:

| 파일 | 타입 | 이유 |
| --- | --- | --- |
| `package.json` 의존성 | build | 산출물에 들어간다 |
| `package.json` 스크립트 이름만 변경 | chore | 빌드 결과는 그대로다 |
| `.gitlab-ci.yml` | ci | CI에서만 쓴다 |
| `Dockerfile` (빌드용) | build | 이미지가 산출물이다 |
| `Dockerfile` (CI 러너용) | ci | 배포 파이프라인 전용이다 |
| `.gitignore` | chore | 어디에도 영향이 없다 |
| `vite.config.ts` | build | 번들 결과가 바뀐다 |
| `tsconfig.json` | build | 컴파일 결과가 바뀐다 |
| `.vscode/settings.json` | chore | 내 에디터만의 일이다 |

## 스코프

괄호 안에 넣어 **어디를 건드렸는지** 한 단어로 알린다.

```
feat(payment): ...
fix(refund): ...
ci(deploy): ...
```

원칙:

- **팀이 미리 정한 목록에서만 고른다.** 아무나 새 스코프를 만들면 아무 의미가 없어진다. 목록은 `docs/`나 CONTRIBUTING에 박아둔다.
- 도메인 단위가 무난하다. `payment`, `refund`, `settlement`, `webhook`, `auth` 같은 것.
- 디렉터리 이름을 그대로 쓰는 것도 흔한 방식이다. 모노레포면 패키지 이름을 쓴다.
- **여러 곳을 건드렸으면 스코프를 여러 개 적지 말고, 커밋을 쪼개라.** `feat(payment,refund):`는 대부분 커밋 하나에 두 가지 일이 들어갔다는 신호다.
- 전역 변경이면 스코프를 생략한다. `style: prettier 적용`처럼.

스코프를 아예 안 쓰는 팀도 많다. 안 쓰기로 정하는 건 괜찮다. **어떤 사람은 쓰고 어떤 사람은 안 쓰는 상태가 최악이다.** 로그를 필터링할 수도, 안 할 수도 없게 된다.

## BREAKING CHANGE

기존에 쓰던 쪽이 **뭔가를 고쳐야만 계속 돌아가는** 변경이다. API 응답 필드 삭제, 함수 시그니처 변경, 설정 키 이름 변경, 기본값 변경.

표기 방법은 두 가지고, 둘 다 써도 된다.

**1. 타입 뒤에 `!`**

```
feat(payment)!: 결제 응답에서 cardNumber 필드 제거
```

**2. 꼬리말에 `BREAKING CHANGE:`**

```
feat(payment): 결제 응답 스키마 정리

카드 정보를 응답에 싣지 않도록 바꿉니다. 전문 조회는 별도
엔드포인트로 분리했습니다.

BREAKING CHANGE: POST /payments 응답에서 cardNumber, cvc가
제거됐습니다. 카드 정보가 필요하면 GET /payments/{id}/card를
호출하세요. 클라이언트 SDK는 2.0 이상이 필요합니다.
```

**권장은 둘 다 쓰는 것이다.** `!`는 로그에서 눈에 띄고, 꼬리말은 릴리즈 노트에 그대로 들어간다.

꼬리말에는 반드시 **뭐가 깨지는지**와 **뭘 해야 하는지**를 적는다. "BREAKING CHANGE: API 변경"만 적힌 커밋은 아무것도 알려주지 않는다.

## 본문과 꼬리말

**본문**은 "왜"를 적는 자리다. "무엇을"은 디프를 보면 안다.

```
fix(payment): 만료월이 12일 때 검증이 통과하던 문제 수정

만료월 비교에 `<` 를 써서 12월 카드가 항상 만료로 처리됐습니다.
경계값 포함이 맞아 `<=` 로 바꿨습니다. 회귀를 막으려고 1월/12월
경계 테스트를 같이 넣었습니다.
```

본문이 필요 없는 커밋도 많다. 제목만으로 충분하면 억지로 쓰지 않는다.

**꼬리말**은 기계가 읽는 자리다. `키: 값` 형식으로 쓴다.

```
Refs: PAY-231
Closes: PAY-231
Co-authored-by: JAY <jay@dalro.example>
Reviewed-by: DEREK <derek@dalro.example>
BREAKING CHANGE: ...
```

- `Refs:` — 관련은 있지만 티켓을 닫지는 않는다. 티켓 하나를 여러 커밋으로 나눌 때 쓴다.
- `Closes:` — 이 커밋으로 티켓이 끝난다. 이슈 트래커가 자동으로 닫아준다.
- 티켓 번호를 제목에 넣는 팀도 있다(`feat(payment): 카드 만료일 검증 추가 (PAY-231)`). 나쁘지 않지만 50자를 먹는다. 꼬리말 쪽을 권한다.

## SemVer와의 연결

타입이 버전의 어느 자리를 올리는지 정해져 있다. `MAJOR.MINOR.PATCH` 기준이다.

| 커밋 | 올라가는 자리 | 예 |
| --- | --- | --- |
| `feat` | MINOR | 1.4.2 → 1.5.0 |
| `fix` | PATCH | 1.4.2 → 1.4.3 |
| `perf` | PATCH | 1.4.2 → 1.4.3 |
| `!` 또는 `BREAKING CHANGE` | MAJOR | 1.4.2 → 2.0.0 |
| `docs` `style` `refactor` `test` `build` `ci` `chore` | 안 올라감 | 1.4.2 그대로 |
| `revert` | 되돌린 커밋을 따라감 | feat를 되돌리면 MINOR |

주의할 점 두 가지.

**MINOR와 PATCH가 섞이면 높은 쪽이 이긴다.** 릴리즈에 feat 1개와 fix 10개가 있으면 MINOR가 올라간다.

**MAJOR는 어디에 붙어도 MAJOR다.** `refactor!:`도 MAJOR를 올린다. 공개 인터페이스가 깨지면 타입과 무관하다.

`0.x`는 예외로 취급하는 팀이 많다. SemVer 명세상 `0.x`에서는 호환성을 보장하지 않아도 되고, 실무에서는 `0.4.0 → 0.5.0`으로 브레이킹을 처리한다.

## 한글 커밋이냐 영어 커밋이냐

정답이 없다. 팀마다 다르고, 둘 다 잘 굴러가는 팀이 있다. 결정 근거만 정리한다.

**한글로 쓸 때**

- 팀원 전부가 한국어 모어 화자면 **의도가 훨씬 정확하게 전달된다.** 영어로 쓰면 "왜"를 설명하다가 어휘가 모자라 두 문장으로 줄여버리는 일이 생긴다.
- 리뷰에서 커밋 메시지를 두고 오해가 줄어든다.
- 신입이 히스토리를 읽고 도메인을 배우기 쉽다. 결제 도메인 용어를 영어로 옮기면 그 자체가 학습 비용이다.
- 단점: 오픈소스로 공개하기 어렵다. 외국인 동료가 합류하면 히스토리 전체가 벽이 된다. 터미널이나 도구에서 폰트·정렬이 깨지는 경우가 아직 있다.

**영어로 쓸 때**

- 공개 저장소로 전환하거나 외부 기여를 받을 여지가 있으면 사실상 필수다.
- 코드 식별자와 문장이 섞였을 때 읽기가 매끄럽다. `fix: return 400 when amount is 0`은 코드 그대로다.
- 커밋 메시지가 짧아진다. 영어 쪽이 명령형으로 압축하기 쉽다.
- 단점: **영어 실력이 메시지 품질의 상한이 된다.** "왜"를 못 적고 "무엇을"만 적게 되는 팀이 실제로 많다. 그러면 컨벤션을 지키는 의미가 절반 날아간다.

**현실적인 절충안** — 실무에서 가장 흔하다.

```
fix(payment): 만료월이 12일 때 검증이 통과하던 문제 수정
```

제목의 **타입과 스코프는 영어, 설명은 한글**로 쓴다. 자동화 도구는 타입만 읽으면 되니 문제없고, 사람은 설명을 모어로 읽는다. 이 교재는 이 방식으로 간다.

정하고 나면 **린터로 강제하는 걸 권한다.** commitlint를 커밋 훅에 걸어두면 논쟁이 사라진다. 사람이 리뷰에서 지적하게 두면 지적하는 사람만 나쁜 사람이 된다.

## 체크리스트

커밋하기 전에 스스로 묻는다.

- [ ] 타입 하나로 이 커밋을 설명할 수 있나? 두 개가 필요하면 커밋을 쪼갠다.
- [ ] 제목만 읽고 무슨 일인지 아나? 50자 안에 들어가나?
- [ ] 이 변경이 왜 필요했는지 본문이 없어도 알 수 있나? 없으면 본문을 쓴다.
- [ ] 공개 인터페이스가 깨지나? 깨지면 `!`와 `BREAKING CHANGE`를 붙인다.
- [ ] 티켓 번호를 꼬리말에 넣었나?
- [ ] 이 커밋만 리버트해도 저장소가 정상인가? 아니면 커밋 경계가 잘못된 것이다.
