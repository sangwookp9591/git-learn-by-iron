# 달로 입사 1주차

## 이 시나리오에 대해

주인공은 **결제 플랫폼 회사 달로(Dalro)의 결제팀에 입사한 신입 백엔드 개발자**다. 학습자가 주인공이다.

Git을 명령어 목록으로 배우면 "언제 쓰는지"가 안 남는다. 그래서 이 교재는 명령을 소개하는 대신 **명령이 필요해지는 상황**을 먼저 만든다. 리베이스를 배우기 전에 main이 앞서가서 곤란해져야 한다.

### 등장인물

주인공은 **IRON**. 이번 주에 결제팀에 들어온 신입 백엔드 개발자이고, 학습자가 곧 IRON이다.

| --- | --- | --- |

**호칭은 이름 + 님으로 통일한다.** 직급으로 부르지 않는다. 팀장님·선임님 같은 호칭은 이 교재에 나오지 않는다. 팀장인 SAM 님도 "SAM 님"이다.

### 배경

- 저장소: `dalro-payments` (GitLab, 그래서 PR이 아니라 **MR**이다)
- 기본 브랜치: `main`. 보호돼 있어서 직접 푸시가 막혀 있다
- 브랜치 규칙: `feature/<티켓>-<짧은설명>`, `hotfix/<티켓>-<짧은설명>`
- 티켓: Jira. 결제팀 접두어는 `PAY-`
- 머지 방식: MR 승인 2개 + CI 통과 후 **스쿼시 머지**
- 릴리즈: 매주 금요일 오전. `vX.Y.Z` 태그를 붙여 배포

### 배우는 명령

```

git config user.email "...@dalro.example"
git log --oneline -10
git branch          # 로컬만

git remote -v
git status
```

`git log`를 첫날에 보는 것도 의도가 있다. 팀의 커밋 컨벤션은 문서보다 히스토리에 더 정확하게 남아 있다. 내일 첫 커밋을 할 때 이 기억이 기준이 된다.

여기서 진짜 배우는 건 명령이 아니라 **순서**다. `main`으로 가서 → 최신으로 맞추고 → 거기서 판다. 이 순서를 건너뛰고 3일 전 `main`에서 브랜치를 파면, 4일차에 충돌로 돌아온다. 6막이 정확히 그 이야기다.

**둘.** 커밋 단위를 나누는 감각. "기능 커밋과 설정 커밋을 나눈다"는 규칙이 아니라 **"하나만 되돌릴 수 있어야 한다"**는 기준을 준다. 5막에서 이 기준이 다시 나온다.

**셋.** 컨벤션은 문서로 읽는 것보다 처음 쓸 때 배우는 게 남는다.

### 상황

어제 커밋 두 개를 만들었다. 오늘 아침 MR을 올린다.

### 대사

> **JAY** — 이제 푸시하실 건데, 처음 올리는 브랜치라 좀 다릅니다. `-u` 붙이세요.

> **IRON** — 그냥 `git push` 하면요?

푸시하고 GitLab에 MR을 연다.

> **JAY** — MR 제목은 커밋 메시지랑 비슷하게 쓰시면 되고, 설명에 뭘 했는지랑 어떻게 확인하는지 적어주세요. 리뷰어가 로컬에서 안 돌려보고도 판단할 수 있게요.
>
> 리뷰어는 저랑 DEREK 님으로 걸어주시고요. CI 돌아가는 거 한번 보세요. 빨간불 뜨면 리뷰 요청하기 전에 먼저 고치는 게 매너예요. 리뷰어 시간 아끼는 거죠.
>
> **IRON** — CI가 얼마나 걸려요?
>
> **JAY** — 4분쯤요. 기다리는 동안 MR 설명 다듬으시면 딱 맞아요. 파이프라인 자체가 이상하게 죽으면 ROWAN 님한테 물어보시면 돼요. 그건 우리가 건드릴 게 아니라서요.

10분 뒤 DEREK 님이 코멘트를 단다.

> **DEREK** — 잘 봤습니다. 로직은 문제없어 보여요. 근데 커밋 하나에 검증 로직이랑 에러 응답 바꾼 게 같이 있어서요, 이거 커밋 좀 나눠주실 수 있을까요? 따로 보면 훨씬 빨리 볼 수 있을 것 같아요.

### 학습자가 할 일

1. 브랜치를 리모트에 푸시하고 추적 관계를 만든다
2. 리모트에 브랜치가 생긴 걸 확인한다
3. MR을 연다 (제목, 설명, 리뷰어 지정)
4. CI 결과를 확인한다
5. 로컬 브랜치와 `origin` 브랜치의 관계를 확인한다

### 배우는 명령

```
git push -u origin feature/PAY-231-card-expiry
git branch -vv                  # 어느 리모트 브랜치를 추적하는지
git log --oneline origin/feature/PAY-231-card-expiry
git status                      # "Your branch is up to date with 'origin/...'"
```

### 왜 지금 이게 필요한가

여기서 **로컬 브랜치와 리모트 브랜치가 다른 것**이라는 사실이 처음 드러난다. `git branch -vv`가 보여주는 `[origin/feature/PAY-231-card-expiry]` 표시가 그 연결이다. 이 개념이 없으면 6막의 "main이 앞서갔다"도, 9막의 "남이 force push 했다"도 이해가 안 된다.

그리고 **MR은 Git 기능이 아니다.** GitLab이 얹은 것이다. Git은 커밋과 브랜치만 알고, 나머지는 도구가 붙인 협업 절차다. 이걸 지금 구분해두면 나중에 "Git이 안 되는 건지 GitLab이 안 되는 건지"를 헷갈리지 않는다.

4. 남은 변경을 담아 두 번째 커밋: `fix(payment): 만료 카드 요청에 400 반환`
5. 커밋 두 개가 각각 무슨 변경을 담고 있는지 확인한다

`fetch`와 `pull`의 차이도 여기가 배울 자리다. 리베이스하려면 최신 `main` 커밋이 로컬에 있어야 하는데, 내 브랜치는 아직 안 움직여야 한다. `fetch`가 정확히 그 일을 한다. `pull`은 `fetch` + `merge`라서 지금 상황에서는 머지 커밋이 생겨버린다.

그리고 **`--abort`를 먼저 알려주는 게 중요하다.** 되돌아갈 수 있다는 걸 알아야 시도를 한다.

> **IRON** — 네 지금 켰습니다.
>
> **SAM** — 급하니까 순서만 짚을게요. `main` 말고 **태그에서** 브랜치 파세요. `v1.9.0`에서요.
>
> **IRON** — `main`에서 따면 안 되나요?
>
> **SAM** — 아까 머지 하나 더 들어갔어요. 그거 아직 검증 안 된 거라서, 핫픽스에 딸려 나가면 안 됩니다. 지금 배포된 상태 그대로에서 딱 이 문제만 고쳐서 나가야 해요.
>
> 고치시고 MR 올려주시면 제가 바로 승인할게요. 오늘은 승인 하나로 갑니다. `v1.9.1` 붙여서 나갑니다.

수정 후.

> **ROWAN** — 배포 태웠습니다. 2분 뒤에 반영돼요.
>
> **SAM** — 실패율 떨어지는 거 확인했습니다. 고생하셨어요.
>
> 마지막 하나만요. 지금 고친 거 `main`에도 들어가야 해요. 안 그러면 다음 배포 때 이 버그가 다시 나갑니다. 핫픽스 커밋을 `main`으로 체리픽해주세요. 그건 월요일에 하셔도 되는데, 오늘 까먹기 전에 티켓만 걸어두시면 좋겠네요.

### 학습자가 할 일

1. 태그 `v1.9.0`에서 핫픽스 브랜치를 판다 (`main`이 아니라)
2. 0-based 만료월 케이스를 처리하고, 회귀 테스트를 추가한다
3. `fix` 타입으로 커밋한다
4. 푸시하고 MR을 올린다
5. 머지 후 `v1.9.1` 태그를 붙여 배포한다
6. 핫픽스 커밋을 `main`에 체리픽한다

### 배우는 명령

```
git fetch origin --tags
git switch -c hotfix/PAY-247-expiry-zero-based v1.9.0
git log --oneline -3                    # v1.9.0 시점 히스토리 확인

# 수정 후
git add src/payment/PaymentValidator.ts \
        src/payment/__tests__/validator.test.ts
git commit -m "fix(payment): 0-based 만료월을 보내는 카드사 요청 처리

일부 해외 카드사가 만료월을 0-11 범위로 보내와 12월 카드가
만료로 처리되고 있었습니다. 게이트웨이 코드로 0-based 여부를
판별해 보정합니다.

Refs: PAY-247"

git push -u origin hotfix/PAY-247-expiry-zero-based
# MR → 머지

git switch main
git pull
git tag -a v1.9.1 -m "핫픽스 1.9.1 — 0-based 만료월 처리 (PAY-247)"
git push origin v1.9.1

# main에 반영
git cherry-pick <핫픽스 커밋 해시>
```

### 왜 지금 이게 필요한가

**핫픽스는 브랜치를 어디서 따느냐가 전부다.** `main`에서 따면 아직 검증 안 된 커밋이 새벽에 운영으로 나간다. 태그에서 따면 지금 돌아가는 코드 그대로에 수정 하나만 얹는다. 7막에서 태그를 붙여둔 게 여기서 회수된다. 태그가 없었으면 "1.9.0이 어느 커밋이었지"부터 뒤져야 한다.

체리픽도 여기가 자연스럽다. 브랜치 전체를 머지하는 게 아니라 **커밋 하나만 골라 다른 브랜치로 옮기는** 상황이 실제로 생긴 것이다. 명령만 먼저 배우면 "이게 언제 필요하지" 싶은데, 핫픽스를 겪고 나면 안 잊는다.

그리고 **핫픽스를 `main`에 반영 안 해서 다음 배포에 버그가 부활하는 사고**는 실제로 흔하다. 대사에 넣어둔 이유다.

## 9막 (보너스) — 동료의 force push 사고

### 상황

다음 주 월요일 아침. `git pull`을 했는데 지난주 커밋이 사라졌다.

### 대사

```
09:12  JAY: 금요일 밤에 PAY-219 브랜치 리베이스하고 강제로 밀었어요
             혹시 그 브랜치 쓰시던 분 계시면 다시 받아주세요
09:38  IRON:   JAY 님 저 hotfix/PAY-247 브랜치 커밋 3개가 없어졌는데요
09:39  JAY: 네? 잠시만요
09:41  JAY: 아 제가 브랜치를 잘못 봤나 봐요... 죄송합니다
             복구 되나요?
09:42  IRON:   찾아볼게요
```

> **JAY** — 정말 죄송해요. 제가 `--force`로 밀었는데, 브랜치 확인을 제대로 안 했어요. `--force-with-lease` 썼으면 막혔을 텐데.
>
> **IRON** — 커밋이 완전히 없어진 건가요?
>
> **JAY** — 제 쪽에서는 그럴 텐데, 혹시 로컬에 브랜치 남아 있으세요?
>
> **IRON** — 있긴 한데 아까 `pull` 해서 리모트랑 맞춰졌어요.
>
> **JAY** — 그럼 `reflog` 보세요. Git이 HEAD 움직인 기록을 따로 남겨둬요. 브랜치에서 떨어져 나간 커밋도 30일까지는 안 지워집니다.

reflog를 확인한다.

```
a91f2c3 HEAD@{0}: pull: Fast-forward
7d4e8b1 HEAD@{1}: commit: test(payment): 0-based 만료월 경계 테스트 추가
3c02af9 HEAD@{2}: commit: fix(payment): 게이트웨이 코드 매핑 보정
e18b77a HEAD@{3}: commit: refactor(payment): 만료월 판별을 별도 함수로 추출
2f9c104 HEAD@{4}: pull: Fast-forward
```

> **IRON** — `HEAD@{1}`이 사라지기 전 위치네요.
>
> **JAY** — 맞아요. 근데 그냥 거기로 리셋하면 안 돼요. 제가 그 사이에 올린 커밋이 날아가요. 이번엔 제가 사고 쳤는데 복구하면서 또 사고 나면 안 되잖아요.
>
> **IRON** — 그럼 어떻게 해요?
>
> **JAY** — 두 갈래를 다 살려야 하니까요. 안전한 순서가 있어요.
>
> 먼저 지금 상태에 이름을 붙여두세요. 브랜치를 하나 더 파는 거예요. 그래야 지금 위치를 잃어버려도 다시 찾아갈 수 있어요.
>
> 그다음에 잃어버린 커밋 3개를 지금 브랜치 위로 체리픽하세요. `reflog`에서 해시 세 개 나왔으니까 순서대로요. 리셋 말고 체리픽이요. 리셋하면 제 커밋이 날아가니까요.

복구 후.

> **JAY** — 확인 좀 해주세요. 제 커밋도 있고 잃어버렸던 3개도 다 있는지요. 테스트도 한 번 돌려보시고요.
>
> **IRON** — 다 있어요. 테스트도 통과합니다.
>
> **JAY** — 다행이네요. 이번 일로 하나만 기억해두세요. `--force` 대신 `--force-with-lease` 쓰세요. 이번에 제가 그거 썼으면 Git이 막아줬어요. 그리고 공용 브랜치는 어떤 옵션으로도 강제 푸시 안 하는 게 맞고요.
>
> 아, 팀에 얘기해서 브랜치 보호 설정도 다시 볼게요. 사람이 조심하는 것보다 설정으로 막는 게 확실하니까요.

### 학습자가 할 일

1. 지금 브랜치가 어디를 가리키는지, 원래 어디였는지 조사한다
2. `reflog`에서 사라지기 전 위치와 잃어버린 커밋 해시를 찾는다
3. **복구 전에 현재 상태를 브랜치로 표시해둔다**
4. 잃어버린 커밋을 지금 브랜치 위로 되살린다 — 동료 커밋도 살아 있어야 한다
5. 히스토리와 워킹 트리가 둘 다 정상인지 확인한다
6. 테스트를 돌린다
7. 안전하게 푸시한다

### 배우는 명령

```
git log --oneline -5
git reflog                              # HEAD가 움직인 기록
git reflog show feature/PAY-219         # 특정 브랜치의 기록

git branch backup/before-recovery       # 지금 위치에 이름 붙이기

git show e18b77a --stat                 # 되살릴 커밋 확인
git cherry-pick e18b77a 3c02af9 7d4e8b1

git log --oneline --graph -10
git status
npm test
git push --force-with-lease

# 다 확인되면
git branch -D backup/before-recovery
```

참고로 알아둘 것:

```
git fsck --lost-found                   # reflog에도 없을 때
git reset --hard ORIG_HEAD              # 직전 위험한 작업 직전으로
```

### 왜 지금 이게 필요한가

**Git에서 커밋은 웬만해서는 안 지워진다.** 이걸 아는 사람과 모르는 사람의 차이가 크다. 모르면 하루 작업을 날렸다고 생각하고 처음부터 다시 짠다. `reflog`는 그 공포를 없애는 명령이다.

이 막이 보너스인 이유는, **1주차 신입이 겪을 일은 아니지만 겪으면 혼자 해결 못 하는 일**이기 때문이다. 미리 한 번 보는 것만으로 대응이 달라진다.

그리고 세 가지가 여기서 회수된다.

- **`--force-with-lease`를 왜 써야 했는지** (5막, 6막) — 이번 사고는 그걸 안 써서 생겼다
- **커밋 되돌리기의 선택** (5막) — `reset`으로 무작정 돌리면 동료 작업이 날아간다. 상황에 맞는 명령을 고르는 게 중급 이상의 판단이다
- **복구 전에 안전지대를 만드는 습관** — `git branch backup/...` 한 줄이다. 복구 중에 실수해도 처음으로 돌아갈 수 있다

마지막으로 대사에 일부러 넣은 게 하나 있다. **JAY 님이 사고를 인정하고, 팀이 설정으로 막자고 결론 내린다.** Git 사고는 개인의 부주의로 끝나지 않고 팀의 규칙으로 정리되는 게 정상이다.
