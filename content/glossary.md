# Git 어휘 기준표

이 교재가 쓰는 한국어 Git 표기를 한곳에 모은 문서다. 기준은 하나다. **한국 개발팀이 실제로 입으로 내뱉는 말**을 쓴다. 사전에 실린 번역어가 아니라, 스탠딩 미팅에서 나오는 말이 기준이다.

표기를 정할 때 쓴 원칙:

1. 명령어 이름에서 온 말은 대체로 음차한다. `git rebase`를 실행하면서 "재배치하겠습니다"라고 말하는 사람은 없다.
2. 상태나 현상을 가리키는 말은 번역어가 살아남은 경우가 많다. 충돌, 저장소, 원격이 그렇다.
3. 둘 다 쓰이는 말은 **혼용**이라고 적고, 교재에서 쓸 한쪽을 골라 끝까지 그걸로 간다. 문서 안에서 왔다 갔다 하는 게 제일 나쁘다.
4. `HEAD`, `origin`, `main`처럼 Git이 정해둔 이름은 건드리지 않는다. 번역도 음차도 하지 않고 원문 그대로 쓴다.

방식 표기는 네 가지다. **음차**(소리대로), **번역**(뜻으로), **혼용**(둘 다 쓰이지만 한쪽을 고름), **원문**(영문 그대로).

## 1. 저장소와 리모트

| 영어 | 우리 표기 | 방식 | 근거 |
| --- | --- | --- | --- |
| repository | 저장소 | 번역 | 문서에서는 저장소가 표준으로 굳었다. 말할 땐 "레포"가 압도적이라 구어로는 레포를 써도 된다. |
| remote | 리모트 | 음차 | "원격"은 "원격 저장소"라는 덩어리로만 살아남았고, `git remote -v`를 두고는 다들 "리모트 확인"이라고 한다. |
| remote repository | 원격 저장소 | 번역 | 이 덩어리만은 번역어가 이겼다. "리모트 저장소"라고 쓰는 문서는 드물다. |
| local | 로컬 | 음차 | 번역어 자체가 없다시피 하다. "내 컴퓨터"라고 풀어 쓰는 게 오히려 어색하다. |
| origin | origin | 원문 | 리모트 이름이지 단어가 아니다. 번역하는 순간 명령어와 안 맞는다. |
| upstream | 업스트림 | 음차 | "상류"는 아무도 안 쓴다. 다만 `@{upstream}` 문법을 말할 때는 원문 그대로 읽는다. |
| downstream | 다운스트림 | 음차 | 업스트림과 짝이라 같이 간다. 실무 등장 빈도는 업스트림보다 훨씬 낮다. |
| clone | 클론 | 음차 | "복제"라고 하면 못 알아듣는다. "저장소 클론 떠 주세요"가 실제 문장이다. |
| fork | 포크 | 음차 | GitHub·GitLab 버튼 이름이 그대로 굳었다. |
| bare repository | 베어 저장소 | 혼용 | "맨 저장소"는 실존하지 않는 말이고, 대부분 그냥 `--bare`라고 부른다. 교재에서는 베어 저장소로 통일한다. |
| submodule | 서브모듈 | 음차 | "하위 모듈"로 쓰면 Git 기능인지 코드 구조인지 구분이 안 된다. |
| worktree | 워크트리 | 음차 | `git worktree`라는 명령 이름이 있어서 음차가 안전하다. 아래 working tree와 헷갈리지 않게 붙여 쓴다. |
| shallow clone | 얕은 클론 | 혼합 | shallow는 번역, clone은 음차. 어정쩡하지만 실제로 이렇게들 말한다. |

## 2. 작업 영역

| 영어 | 우리 표기 | 방식 | 근거 |
| --- | --- | --- | --- |
| working tree | 워킹 트리 | 음차 | "작업 트리"는 번역체 느낌이 강하다. 상태를 말할 땐 "작업 디렉터리"라고 풀기도 한다. |
| working directory | 작업 디렉터리 | 번역 | 워킹 트리와 사실상 같은 걸 가리키지만, 파일 얘기를 할 땐 이쪽이 더 자연스럽다. |
| staging area | 스테이징 영역 | 혼용 | "준비 영역"은 죽은 말이고, 현장에서는 그냥 "스테이지"나 "add한 상태"라고 한다. 교재에서는 스테이징 영역으로 고정한다. |
| index | 인덱스 | 음차 | 스테이징 영역과 같은 것을 가리키는 Git 내부 용어. 에러 메시지에 `index`가 그대로 나오니 음차가 낫다. |
| stage (동사) | 스테이징하다 | 음차 | 실제로는 "add한다"가 더 많이 쓰인다. 명령을 가리킬 땐 add, 개념을 가리킬 땐 스테이징으로 나눠 쓴다. |
| unstage | 스테이징 취소 | 혼합 | "언스테이지"도 쓰이지만 어감이 낯설다. "add 취소"가 구어에서는 가장 흔하다. |
| tracked | 추적 중인 파일 | 번역 | 번역어가 자리 잡았다. Git이 알고 있는 파일이라는 뜻이 그대로 전달된다. |
| untracked | 추적 안 되는 파일 | 번역 | `git status`의 Untracked files를 설명할 때 그대로 읽어도 통한다. |
| stash | 스태시 | 음차 | "임시 보관"은 설명이지 용어가 아니다. 표기는 스태시와 스태쉬가 섞이는데 스태시로 간다. |
| clean (상태) | 깨끗하다 | 번역 | "워킹 트리 깨끗해요"가 실제 문장이다. 명령 `git clean`과는 다른 말이니 문맥으로 구분한다. |
| dirty (상태) | 변경사항이 남아 있다 | 풀어 씀 | "더럽다"는 안 쓴다. 상태를 그대로 풀어 설명하는 게 가장 잘 통한다. |
| .gitignore | 깃이그노어 / `.gitignore` | 원문 | 파일 이름이라 원문이 원칙이다. 말할 땐 "깃이그노어에 넣어주세요"라고 한다. |

## 3. 커밋과 히스토리

| 영어 | 우리 표기 | 방식 | 근거 |
| --- | --- | --- | --- |
| commit | 커밋 | 음차 | 번역 논의 자체가 없다. 명사·동사 모두 "커밋한다"로 쓴다. |
| commit message | 커밋 메시지 | 음차 | 통째로 음차된 덩어리다. |
| commit hash | 커밋 해시 | 혼합 | "해시값", "SHA", "커밋 아이디"가 다 쓰인다. 교재에서는 커밋 해시로 통일한다. |
| SHA | SHA | 원문 | 약어라 그대로 읽는다. "샤"라고 발음하는 사람과 "에스에이치에이"가 섞이는데 표기는 SHA다. |
| parent commit | 부모 커밋 | 번역 | 번역어가 완승했다. 조상/자손 비유가 그대로 통한다. |
| ancestor | 조상 커밋 | 번역 | 위와 같은 이유다. |
| history | 히스토리 | 혼용 | "이력"도 쓰이지만 "커밋 히스토리"라는 덩어리가 더 익숙하다. 교재는 히스토리로 간다. |
| log | 로그 | 음차 | `git log` 그대로. 애플리케이션 로그와 헷갈릴 땐 "커밋 로그"라고 붙인다. |
| diff | 디프 | 혼용 | "변경분", "차이"로 풀기도 하지만 "디프 좀 볼게요"가 제일 자연스럽다. 표기는 디프로 고정하되 명령은 `git diff`로 쓴다. |
| hunk | 헝크 | 음차 | 번역어가 아예 없다. `git add -p`가 잘라주는 덩어리를 가리키는 말로 음차가 유일한 선택이다. |
| patch | 패치 | 음차 | fetch와 발음이 겹쳐 혼동이 잦다. 교재에서는 패치는 `.patch` 파일과 `-p` 모드에만 쓴다. |
| blame | 블레임 | 음차 | "누가 썼는지 보기"로 풀면 길다. "블레임 떠보니까"라는 말이 실제로 오간다. |
| bisect | 바이섹트 | 음차 | "이분 탐색"은 알고리즘 얘기가 되어버린다. 명령 이름 그대로 간다. |
| amend | 어멘드 | 혼용 | "커밋 수정"으로 풀기도 한다. `--amend` 옵션 자체를 가리킬 땐 어멘드, 행위를 말할 땐 "직전 커밋 고치기"로 쓴다. |
| snapshot | 스냅샷 | 음차 | 커밋이 스냅샷이라는 설명에서 빠지지 않는데, 번역어가 없다. |
| dangling commit | 떠도는 커밋 | 번역 | "댕글링 커밋"도 쓰이지만, 복구 상황을 설명할 땐 번역어가 훨씬 빨리 이해된다. |

## 4. 브랜치와 참조

| 영어 | 우리 표기 | 방식 | 근거 |
| --- | --- | --- | --- |
| branch | 브랜치 | 음차 | "가지"는 농담으로만 쓴다. 동사로는 "브랜치를 판다"는 관용구가 있다. |
| default branch | 기본 브랜치 | 번역 | 번역어가 자연스럽고 짧다. |
| main | main | 원문 | 브랜치 이름이라 건드리지 않는다. 오래된 저장소는 `master`인데 그것도 그대로 쓴다. |
| feature branch | 피처 브랜치 | 음차 | "기능 브랜치"는 문서에서만 보인다. |
| tracking branch | 추적 브랜치 | 번역 | "트래킹 브랜치"도 쓰이지만, `-u` 옵션을 설명할 땐 번역어 쪽이 뜻이 바로 온다. |
| HEAD | HEAD | 원문 | 번역도 음차도 하지 않는다. 대문자 네 글자 그대로 쓰고 "헤드"라고 읽는다. |
| detached HEAD | 디태치드 HEAD | 혼합 | "분리된 HEAD"는 문서에서만 보인다. Git이 그대로 뱉는 문구라 음차 쪽이 검색도 잘 된다. |
| ref | ref | 원문 | `refs/heads/...` 경로에 그대로 나오는 말이라 번역하면 오히려 안 맞는다. |
| reflog | 리플로그 | 음차 | "참조 로그"라고 쓰면 무슨 기능인지 아무도 모른다. 복구 얘기의 핵심 단어라 음차로 고정한다. |
| tag | 태그 | 음차 | 번역 시도 자체가 없었다. |
| annotated tag | 어노테이티드 태그 | 음차 | 길지만 `-a` 옵션을 설명하려면 원어를 붙잡는 게 낫다. |
| lightweight tag | 라이트웨이트 태그 | 음차 | 위와 짝이라 같은 방식으로 간다. |
| checkout | 체크아웃 | 음차 | 명령 이름 그대로. 요즘은 `switch`/`restore`로 쪼개졌지만 말은 여전히 "체크아웃"이다. |
| switch | 브랜치 전환 | 혼용 | 명령은 `git switch`, 행위는 "브랜치 갈아타기"나 "전환"으로 부른다. 이건 아직 굳지 않았다. |

## 5. 합치기와 되돌리기

| 영어 | 우리 표기 | 방식 | 근거 |
| --- | --- | --- | --- |
| merge | 머지 | 음차 | 번역어 "병합"은 문서에서만 살아 있고 말할 땐 아무도 안 쓴다. "머지 쳐주세요"가 실제 문장이다. |
| merge commit | 머지 커밋 | 음차 | 통째로 굳은 덩어리다. |
| fast-forward | 패스트 포워드 | 음차 | "빨리 감기"로 쓰면 비디오 얘기가 된다. 줄여서 "FF"라고도 한다. |
| three-way merge | 3-way 머지 | 혼합 | 숫자는 아라비아 숫자, 나머지는 음차. "삼방향 병합"은 아무도 안 쓴다. |
| conflict | 충돌 | 번역 | **번역어가 이긴 대표 사례다.** "컨플릭트"도 쓰이지만 "충돌 났어요"가 압도적이다. |
| resolve (conflict) | 충돌 해결 | 번역 | 충돌이 번역어로 굳었으니 짝도 번역어로 간다. |
| conflict marker | 충돌 표시 | 번역 | `<<<<<<<` 기호를 가리킨다. "마커"라고도 하지만 초보 설명에는 번역어가 낫다. |
| rebase | 리베이스 | 음차 | "재배치"는 실존하지 않는 말이다. 동사로 "리베이스한다"로 쓴다. |
| interactive rebase | 인터랙티브 리베이스 | 음차 | 줄여서 "리베이스 -i"라고 부르는 경우가 더 많다. |
| cherry-pick | 체리픽 | 음차 | 하이픈은 명령에만 남기고 우리말 표기에서는 붙여 쓴다. |
| squash | 스쿼시 | 음차 | "압축"은 파일 압축과 헷갈린다. "스쿼시 머지"가 한 덩어리로 굳었다. |
| fixup | 픽스업 | 음차 | `--fixup`과 리베이스 todo의 `fixup`을 그대로 읽는다. |
| revert | 리버트 | 음차 | "되돌리기"라고 하면 `reset`인지 `revert`인지 구분이 안 된다. 명령을 가리킬 땐 반드시 리버트로 쓴다. |
| reset | 리셋 | 음차 | 위와 같은 이유다. `--soft`/`--mixed`/`--hard`는 옵션 이름 그대로 읽는다. |
| restore | 리스토어 | 음차 | 아직 덜 퍼진 명령이라 음차로 두고, 설명할 땐 "파일 되돌리기"로 푼다. |
| drop (stash/rebase) | 드롭 | 음차 | 짧고 오해의 여지가 없다. |

## 6. 주고받기와 협업

| 영어 | 우리 표기 | 방식 | 근거 |
| --- | --- | --- | --- |
| fetch | 페치 | 음차 | "패치(patch)"와 발음이 겹치니 표기를 페치로 못 박는다. "가져오기"는 pull과 구분이 안 된다. |
| pull | 풀 | 음차 | "당겨오기"는 농담으로만 쓴다. |
| push | 푸시 | 음차 | "푸쉬"와 흔들리는데 외래어 표기법에 맞춰 푸시로 고정한다. |
| force push | 포스 푸시 | 음차 | "강제 푸시"도 쓰인다. 사고 얘기를 할 땐 "강제로 밀었다"처럼 풀어 쓰기도 한다. |
| pull request | 풀 리퀘스트 / PR | 음차 | GitHub 기능 이름이라 번역하지 않는다. 대화에서는 거의 항상 "PR"이다. |
| merge request | 머지 리퀘스트 / MR | 음차 | GitLab 쪽 이름. 이 교재의 회사는 GitLab을 쓰므로 MR로 간다. |
| review | 리뷰 | 음차 | "검토"는 결재 문서 냄새가 난다. |
| reviewer | 리뷰어 | 음차 | 위와 같다. |
| approve | 어프루브 / 승인 | 혼용 | 버튼을 누르는 행위는 "어프루브", 절차를 말할 땐 "승인"이 자연스럽다. |
| LGTM | LGTM | 원문 | 약어 그대로 쓴다. 풀어 쓸 필요를 아무도 못 느낀다. |
| WIP | WIP | 원문 | MR 제목 접두어로 쓰이는 관용 약어다. |
| hotfix | 핫픽스 | 음차 | "긴급 수정"으로 풀기도 하지만 브랜치 이름이 `hotfix/`라 음차가 편하다. |
| release | 릴리즈 | 음차 | 외래어 표기법은 "릴리스"지만 현장에서는 "릴리즈"가 압도적이다. 이 교재는 현장 쪽을 따른다. |
| hook | 훅 | 음차 | `.git/hooks`에 있는 그것. React 훅과 헷갈릴 땐 "깃 훅"이라고 붙인다. |
| CI | CI | 원문 | 약어를 풀어 쓰는 사람이 없다. |
| prune | 프룬 | 음차 | `--prune`을 설명할 땐 "리모트에서 사라진 브랜치 정리"라고 풀어준다. |

## 표기가 흔들리는 것들 — 이 교재의 결정

어느 쪽도 틀리지 않는 항목이 있다. 이럴 땐 "둘 다 쓰인다"는 사실을 적어두고 한쪽을 골라 끝까지 그걸로 간다.

| 흔들리는 표기 | 이 교재의 선택 | 왜 |
| --- | --- | --- |
| 푸시 / 푸쉬 | **푸시** | 외래어 표기법에 맞다. 검색 결과도 푸시가 더 많다. |
| 릴리스 / 릴리즈 | **릴리즈** | 여기서는 표기법보다 현장 말을 택했다. 발표 자료에 "릴리스"라고 쓰는 팀은 드물다. |
| 스태시 / 스태쉬 | **스태시** | 푸시와 같은 기준이다. `sh` 받침을 "시"로 적는 쪽으로 통일한다. |
| 디렉터리 / 디렉토리 | **디렉터리** | 표기법 기준. 다만 구어로 "디렉토리"라고 말하는 건 그대로 둔다. |
| 머지 / 병합 | **머지** | 말할 때 병합이라고 하는 사람이 없다. 문서만 다르게 쓰면 따로 논다. |
| 충돌 / 컨플릭트 | **충돌** | 반대로 여기선 번역어가 이겼다. 규칙보다 실제 사용이 우선이다. |
| 커밋 해시 / SHA / 커밋 ID | **커밋 해시** | 셋 다 통하지만 초보에게 가장 덜 위협적이다. |
| 레포 / 저장소 | **저장소** | 문서 표기는 저장소, 대사 안에서 인물이 말할 땐 "레포"를 그대로 쓴다. |
| 브랜치 딴다 / 브랜치 만든다 | **브랜치를 판다** | 관용구다. 교재 대사에서는 이 말을 그대로 쓴다. |

## 번역하지 않는 것들

다음은 번역도 음차도 하지 않고 영문 그대로 쓴다. Git이 화면에 그대로 뱉는 이름이고, 바꾸는 순간 학습자가 터미널 출력과 대조하지 못한다.

`HEAD` · `ORIG_HEAD` · `FETCH_HEAD` · `MERGE_HEAD` · `origin` · `main` · `master` · `refs/heads` · `refs/remotes` · `.git` · `.gitignore` · `index` (파일로서의 `.git/index`) · 모든 명령어와 옵션 문자열

## 이 기준표를 쓰는 법

교재를 새로 쓰거나 고칠 때 용어가 헷갈리면 여기를 먼저 본다. 표에 없는 말이 필요하면 원칙 1~4로 판단하고, 판단한 결과를 이 문서에 한 줄 추가한다. **기준표에 없는 말을 본문에서 즉흥적으로 정하는 것이 이 교재가 망가지는 가장 흔한 경로다.**
