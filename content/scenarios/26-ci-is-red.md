# 26 — CI 가 깨졌다

> ### 이 시나리오에서 배우는 것
>
> - **배우는 명령** — `git log --oneline origin/main..HEAD` · `git switch --detach` · `git stash` · `git diff origin/main...HEAD -- <경로>` · `git commit --amend` · `git push --force-with-lease` · `git revert`
> - **배우는 개념** — **내 변경이 깬 것과 원래 깨져 있던 것을 가르는 순서.** 로컬에서 재현되지 않는 실패를 좁히는 법. 파이프라인은 Git이 아니라 도구가 얹은 것이다.
> - **끝내면 할 수 있는 일** — 빨간불이 떴을 때 원인이 내 쪽인지 아닌지를 먼저 판정하고, 리뷰를 요청하기 전에 초록불을 만들어놓을 수 있다.

## 학습자가 할 일

1. 실패한 잡과 실패한 테스트를 구분해서 적는다 — **몇 개가 왜 깨졌는지 먼저 센다**
2. 기준 브랜치의 최근 파이프라인을 확인해 **내 커밋 없이도 깨지는지** 판정한다
3. 내 책임이 아닌 실패는 채널에 알린다. 혼자 고치려 들지 않는다
4. 내 책임인 실패는, 먼저 **CI가 돌린 코드와 내 로컬이 같은지** 확인한다
5. 커밋 안 된 파일이 있으면 그것부터 처리한다
6. 그래도 로컬에서 재현이 안 되면 커밋 단위로 범위를 좁힌다 — 브랜치를 만들지 않고, 하던 작업은 잠깐 치워둔다
7. 원인 커밋을 찾으면 수정을 그 커밋에 넣을지 새로 얹을지 판단한다
8. 남은 빨간불이 내 것이 아니면 **MR 설명에 근거와 함께 적는다**
9. 기준 브랜치가 고쳐지면 받아와서 다시 돌린다

## 배우는 명령

```
# 1. 내 브랜치가 무엇을 바꿨는지 정확히
git log --oneline origin/main..HEAD
git diff --stat origin/main...HEAD

# 2. CI가 돌린 것과 내 로컬이 같은가
git status
git diff                                # 커밋 안 된 변경
git log --oneline origin/feature/PAY-268-settlement-batch..HEAD   # 푸시 안 한 커밋

# 3. 커밋 단위로 좁히기 — 하던 작업은 치워두고
git stash push -m "정산 재처리 작업 중"
git switch --detach HEAD~3
npm test
git switch --detach HEAD~2
npm test
git switch -
git stash pop

# 4. 원인 커밋에 수정을 넣기
git add src/settlement/__tests__/batch.test.ts
git commit --fixup <원인커밋>
git rebase -i --autosquash origin/main
git push --force-with-lease

# 5. main이 고쳐진 뒤 따라잡기
git fetch origin
git rebase origin/main
git push --force-with-lease
```

커밋이 많아 손으로 못 좁힐 때는 45번으로 넘어간다.

```
git bisect start
git bisect bad HEAD
git bisect good origin/main
git bisect run npm test
git bisect reset
```

## 왜 지금 이게 필요한가

**빨간불 앞에서 신입이 하는 첫 실수는 바로 고치려 드는 것이다.** 실패 로그를 열고 눈에 띄는 테스트부터 손을 댄다. 그런데 이 시나리오처럼 실패 두 개 중 하나가 남의 문제인 경우, 그렇게 시작하면 두 시간을 남의 버그에 쓴다.

그래서 이 시나리오의 핵심은 명령이 아니라 **순서**다.

1. 몇 개가 깨졌는지 센다
2. 내 커밋 없이도 깨지는지 본다 → 아니면 알린다
3. CI가 돌린 코드와 내 로컬이 같은지 본다
4. 그래도 재현이 안 되면 범위를 좁힌다

**3번이 특히 중요하다.** "로컬에서는 되는데요"의 절반은 커밋 안 된 파일이다. 이건 Git 문제지 CI 문제가 아닌데, CI 로그만 들여다보면 절대 안 보인다. 신입이 `git status`를 습관으로 보지 않으면 이걸 몇 번이고 반복한다. 3막에서 `git status`부터 보라고 배운 게 여기서 회수된다.

**"내 책임이 아니면 알린다"를 명령과 같은 무게로 넣은 것도 의도다.** `main`이 깨져 있으면 팀 전체 MR이 빨갛다. 먼저 발견한 사람이 말 안 하면 여러 명이 같은 조사를 따로 한다. 그리고 반대로, 남의 문제를 혼자 고치겠다고 `main`을 건드리는 것도 사고다. ROWAN 님이 리버트로 정리한 건 **결정 권한이 있는 사람이 정리하는 게 맞다**는 그림이다.

디태치드 HEAD로 커밋을 하나씩 돌려보는 방법은 23번에서 배운 것의 재사용이다. 거기서는 남의 MR을 읽으려고 썼고, 여기서는 내 커밋을 되짚으려고 쓴다. **같은 도구가 다른 목적에 쓰이는 걸 보면 그게 도구로 자리 잡는다.** 45번 바이섹트는 이 수동 좁히기를 자동화한 것이라, 여기서 손으로 해봐야 바이섹트가 뭘 대신해주는지 안다.

마지막으로 **MR 설명에 근거를 적는 것.** 4막에서 JAY 님이 "빨간불 뜨면 리뷰 요청 전에 고치는 게 매너"라고 했다. 그런데 못 고치는 빨간불도 있다. 그럴 땐 고치는 대신 **왜 빨간지 리뷰어가 조사 안 해도 되게** 만든다. 이게 그 규칙의 정확한 적용이다.
