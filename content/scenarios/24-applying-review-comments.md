# 24 — 리뷰 코멘트를 받고 반영해서 다시 올린다

> ### 이 시나리오에서 배우는 것
>
> - **배우는 명령** — `git add -p` · `git commit` · `git commit --fixup` · `git rebase -i --autosquash` · `git log --oneline origin/<브랜치>..HEAD` · `git push` · `git push --force-with-lease`
> - **배우는 개념** — 리뷰 반영을 **새 커밋으로 남길지 원래 커밋에 접을지**의 판단 기준. 히스토리를 고치면 그냥 푸시가 거절되는 이유. `--force`와 `--force-with-lease`의 차이.
> - **끝내면 할 수 있는 일** — 리뷰 코멘트 여러 개를 성격별로 나눠 반영하고, 리뷰어가 무엇이 달라졌는지 바로 알 수 있는 상태로 다시 올릴 수 있다.

## 대사

> **IRON** — 코멘트 네 개 받았는데요. 고치는 건 알겠는데 커밋을 어떻게 해야 할지 모르겠어요. 그냥 "리뷰 반영" 커밋 하나 만들면 되나요?
>
> **JAY** — 그게 제일 흔한 방법이긴 한데, 지금은 좀 아까워요. 코멘트가 성격이 나뉘거든요.
>
> **IRON** — 나뉘어요?
>
> **JAY** — 네 개 중에 둘은 `[blocking]`이고 둘은 `[nit]`이잖아요. 백오프 바꾸는 거랑 실패 테스트 추가하는 건 **동작이 바뀌는 거예요.** 이름 바꾸고 주석 지우는 건 동작이 안 바뀌고요.
>
> 그리고 하나 더 봐야 할 게 있어요. 지금 커밋이 세 개죠? 어느 커밋에 대한 코멘트인지 보세요.

```
$ git log --oneline origin/main..HEAD
3a91c7d test(webhook): 환불 웹훅 발송 테스트 추가
81f0e42 feat(webhook): 환불 완료 웹훅 발송 추가
c04ab19 refactor(webhook): 웹훅 전송을 WebhookSender로 분리
```

> **JAY** — 백오프랑 이름은 `81f0e42`, 그러니까 기능 커밋 얘기예요. 실패 테스트는 `3a91c7d` 테스트 커밋 얘기고요.
>
> **IRON** — 그럼 그 커밋들을 고쳐야 하나요?
>
> **JAY** — 거기서 판단이 갈려요. 두 가지 방법이 있고, 저희 팀은 상황 봐서 골라요.

### 방법 하나 — 반영 커밋을 새로 얹는다

> **JAY** — 제일 단순해요. 지금 커밋 세 개는 그대로 두고, 반영한 걸 커밋 하나로 위에 얹는 거예요. 그리고 그냥 `git push` 하면 끝이고요.
>
> **IRON** — 강제 푸시가 필요 없는 거네요.
>
> **JAY** — 네. 히스토리를 안 건드리니까요. 그리고 **리뷰어한테 제일 친절해요.** DEREK 님이 다시 볼 때 "새로 올라온 커밋 하나만 보면 되네" 하고 끝나거든요. 아까 전체를 다시 볼 필요가 없어요.
>
> **IRON** — 그럼 이게 좋은 거 아니에요?
>
> **JAY** — 리뷰 보기엔 좋은데, `main`에 남기엔 안 좋아요. "리뷰 반영" 커밋이 히스토리에 남으면 나중에 아무 의미가 없어요. 3개월 뒤에 `git log` 보는 사람한테 "리뷰 반영"이 무슨 정보겠어요.
>
> **IRON** — 아 그런데 저희 팀은 스쿼시 머지잖아요. 어차피 합쳐지지 않나요?
>
> **JAY** — 맞아요. **그래서 저희 팀에선 이 방법이 대부분 괜찮아요.** 스쿼시로 하나가 되니까 중간 커밋이 `main`에 안 남거든요. 커밋을 그대로 남기는 팀이면 얘기가 다르고요.

### 방법 둘 — 원래 커밋에 접어 넣는다

> **JAY** — 다른 방법은 반영 내용을 원래 커밋에 넣어버리는 거예요. 백오프 수정은 `81f0e42` 안으로, 실패 테스트는 `3a91c7d` 안으로요.
>
> **IRON** — 그럼 커밋이 계속 세 개인 거네요.
>
> **JAY** — 네. 리베이스 대상 커밋을 손으로 지정해도 되는데, 그러면 어느 커밋에 넣을지 매번 생각해야 해요. `--fixup`을 쓰면 편해요.
>
> 고친 다음에 `git commit --fixup 81f0e42` 이렇게 하면 "이건 `81f0e42`에 합칠 거다"라고 표시된 커밋이 만들어져요. 제목이 `fixup! feat(webhook): ...` 이렇게 붙고요.
>
> **IRON** — 그럼 커밋이 늘어나는 거 아닌가요?
>
> **JAY** — 일단 늘어요. 그러다 마지막에 `git rebase -i --autosquash origin/main` 하면 Git이 표시를 보고 알아서 제자리에 끼워 넣어요. 순서 맞추는 걸 손으로 안 해도 돼요.
>
> **IRON** — 그럼 커밋 해시가 바뀌겠네요.
>
> **JAY** — 네. 그래서 그냥 푸시하면 거절당해요.

### 거절당하는 순간

IRON이 시험 삼아 두 번째 방법을 써보고 푸시한다.

```
$ git push
To gitlab.dalro.example:payments/dalro-payments.git
 ! [rejected]        feature/PAY-261-refund-webhook -> feature/PAY-261-refund-webhook (non-fast-forward)
error: failed to push some refs to 'gitlab.dalro.example:payments/dalro-payments.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart.
```

> **IRON** — 거절당했어요. 뒤처져 있다는데, 저는 커밋을 더 만들었는데요.
>
> **JAY** — Git 입장에선 그렇게 보여요. 리모트에 있는 커밋 세 개가 제 로컬 히스토리 어디에도 없거든요. 접어 넣으면서 다른 커밋이 됐으니까요. Git은 "네가 밀면 저기 있는 커밋 셋이 없어지는데 괜찮냐"고 막는 거예요.
>
> **IRON** — 그럼 `--force`요?
>
> **JAY** — `--force-with-lease`요. **`--force`는 쓰지 마세요.**
>
> `--force`는 리모트에 뭐가 있든 무조건 덮어써요. 그사이에 누가 그 브랜치에 뭘 올렸으면 그대로 날아가요. `--force-with-lease`는 "내가 마지막으로 본 상태랑 리모트가 지금도 같으면 덮어써"예요. 그사이에 바뀌었으면 거절합니다.
>
> **IRON** — 제 브랜치인데 누가 올려요?
>
> **JAY** — 지금은 없을 수도 있어요. 근데 4번 상황처럼 누가 이어받아서 작업하는 경우도 있고, 리뷰어가 오타 하나 GitLab에서 직접 고쳐서 커밋하는 경우도 있어요. 그거 은근히 흔해요.
>
> 그리고 습관의 문제예요. **평소에 `--force-with-lease`를 쓰는 사람이 사고를 덜 냅니다.** 9막에서 볼 그 사고도 `--force` 때문이었어요.

## 학습자가 할 일

1. 코멘트를 **동작이 바뀌는 것과 안 바뀌는 것**으로 나눈다
2. 각 코멘트가 어느 커밋에 대한 것인지 로그에서 확인한다
3. 수정하고, 한 파일 안에 성격이 다른 수정이 섞였으면 골라서 담는다
4. 방법 하나로 먼저 처리한다 — 반영 커밋을 새로 얹고 그냥 푸시한다
5. 되돌린 뒤, 같은 반영을 방법 둘로 처리한다 — 각 수정을 원래 커밋에 합치도록 표시해 커밋한다
6. 표시한 커밋들을 원래 자리에 접어 넣는다
7. 그냥 푸시해보고 **거절 메시지를 읽는다.** 왜 "뒤처졌다"고 하는지 설명해본다
8. 안전한 방식으로 다시 푸시한다
9. 코멘트마다 어떻게 반영했는지 답을 남긴다. 안 고친 것도 이유를 남긴다

## 배우는 명령

```
git log --oneline origin/main..HEAD             # 내 커밋들
git log --oneline origin/feature/PAY-261-refund-webhook..HEAD   # 아직 안 올린 것

# 수정 후 — 한 파일에 섞였으면 골라 담기
git add -p src/webhook/WebhookSender.ts
git diff --staged

# 방법 하나 — 반영 커밋을 얹는다
git commit -m "fix(webhook): 재시도 간격을 지수 백오프로 변경

Refs: PAY-261"
git push

# 되돌리기
git reset --hard origin/feature/PAY-261-refund-webhook

# 방법 둘 — 원래 커밋에 접어 넣는다
git commit --fixup 81f0e42
git commit --fixup 3a91c7d
git log --oneline -6                            # fixup! 커밋이 보인다
git rebase -i --autosquash origin/main
git log --oneline origin/main..HEAD             # 다시 3개, 해시는 전부 바뀜

git push                                        # 거절된다 (non-fast-forward)
git push --force-with-lease                     # 이걸 쓴다
```

`--force`와 `--force-with-lease`의 차이를 직접 본다.

```
git push --force-with-lease                     # 리모트가 내가 아는 상태와 다르면 stale info로 거절
git fetch origin                                # 다시 확인한 뒤
git log --oneline origin/feature/PAY-261-refund-webhook
```

## 왜 지금 이게 필요한가

**리뷰 반영은 1주차 신입이 가장 먼저 겪는 "이미 올린 것을 고치는 일"이다.** 여기서 처음으로 히스토리를 다시 쓰게 되고, 처음으로 푸시가 거절당한다. 이 두 가지가 같은 사건의 앞뒤라는 걸 여기서 잡아야 25번, 39번이 이어진다.

이 시나리오가 단순히 "`--fixup`을 배운다"가 아닌 이유는, **두 방법 중에 고르는 것 자체가 배울 내용**이기 때문이다.

방법 하나(반영 커밋 얹기)는 리뷰어에게 친절하고 안전하다. 방법 둘(접어 넣기)은 히스토리가 깨끗하지만 리뷰어가 다시 읽어야 하고 강제 푸시가 필요하다. **어느 쪽이 맞는지는 팀의 머지 전략이 정한다.** 스쿼시 머지를 쓰면 중간 커밋이 어차피 사라지니까 방법 하나로 충분하다. 커밋을 그대로 남기는 팀이면 방법 둘이 필요하다. 명령을 가르치기 전에 이 연결을 보여줘야 "왜 팀마다 다르게 하지"라는 혼란이 안 생긴다. 27번(머지 전략 고르기)에서 이 판단이 다시 나온다.

**푸시 거절 메시지를 직접 읽게 하는 것도 의도다.** `non-fast-forward`와 "your branch is behind"는 신입 입장에서 말이 안 되는 문장이다. 나는 커밋을 더 만들었는데 왜 뒤처졌다는 건가. 이 문장이 이해되는 순간이 **로컬 브랜치와 리모트 브랜치가 정말로 다른 것**이라는 사실이 몸에 들어오는 순간이다. 4막에서 `git branch -vv`로 본 그 연결선이 여기서 회수된다.

`--force-with-lease`를 쓰는 이유를 "지금 당장의 위험"이 아니라 **습관**으로 설명한 것도 일부러다. 실제로 내 피처 브랜치를 남이 건드릴 일은 드물다. 그래서 "지금은 괜찮으니까 `--force`"가 되고, 그 손버릇이 공용 브랜치에서 사고를 낸다. 9막의 JAY 님이 정확히 그랬다.

마지막으로 DEREK 님 대사의 **"답은 해주세요"**. 코멘트를 다 반영할 필요는 없지만 침묵은 안 된다. 이건 Git 기능이 아니지만 리뷰 왕복 횟수를 절반으로 줄이는 것이고, 명령보다 먼저 배워야 할 때가 많다.
