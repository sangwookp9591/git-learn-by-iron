# 23 — 내가 남의 MR 을 리뷰한다

> ### 이 시나리오에서 배우는 것
>
> - **배우는 명령** — `git fetch origin` · `git switch --detach origin/<브랜치>` · `git log --oneline main..origin/<브랜치>` · `git diff main...origin/<브랜치>` · `git show` · `git range-diff` · `git switch -`
> - **배우는 개념** — 두 점 `..`과 세 점 `...`의 차이. 리뷰는 최종 디프가 아니라 **커밋이 쌓인 순서**로 읽는다. 로컬에서 남의 브랜치를 보는 것과 받아오는 것은 다르다.
> - **끝내면 할 수 있는 일** — 남의 MR을 내 컴퓨터에서 실제로 돌려보면서 작업 순서대로 읽고, 근거가 붙은 리뷰 코멘트를 남길 수 있다.

2주차 화요일 오전. 알림이 왔다. NOAH 님이 올린 MR에 내가 리뷰어로 걸렸다.

```

!412  feat(refund): 부분 환불 취소 API 추가
      feature/PAY-256-partial-refund-cancel → main

```

지금까지는 리뷰를 받기만 했다. 남의 것을 보는 건 처음이다.

## 학습자가 할 일

1. 리뷰할 브랜치를 로컬로 받아온다 — **내 브랜치는 건드리지 않는다**
2. 그 브랜치에만 있는 커밋을 순서대로 뽑아 작업의 흐름을 읽는다
3. 커밋을 하나씩 열어 각 커밋이 스스로 말이 되는지 본다 (리팩터 커밋에 기능이 섞여 있지 않은지)
4. 브랜치를 새로 만들지 않고 그 위치로 이동해 실제로 테스트를 돌려본다
5. 갈라진 지점 기준으로 전체 디프를 뽑아 `main`의 다른 변경이 섞이지 않았는지 확인한다
6. 막는 코멘트와 취향 코멘트를 구분해서, 줄을 찍고 이유를 붙여 남긴다
7. 잘한 부분을 최소 하나 적는다
8. 원래 작업하던 자리로 돌아온다
9. 재푸시된 뒤에는 **이전 버전과 새 버전의 커밋을 짝지어** 무엇이 달라졌는지 확인한다

## 배우는 명령

```
git fetch origin

# 그 브랜치에만 있는 커밋 — 로그는 점 두 개
git log --oneline main..origin/feature/PAY-256-partial-refund-cancel
git log --stat main..origin/feature/PAY-256-partial-refund-cancel

# 커밋 하나씩 읽기
git show origin/feature/PAY-256-partial-refund-cancel~5
git show --stat origin/feature/PAY-256-partial-refund-cancel

# 전체 디프 — 디프는 점 세 개
git diff main...origin/feature/PAY-256-partial-refund-cancel
git diff --stat main...origin/feature/PAY-256-partial-refund-cancel

# 브랜치를 만들지 않고 그 위치로
git switch --detach origin/feature/PAY-256-partial-refund-cancel
npm test
git switch -                            # 원래 자리로

# 재푸시된 뒤 무엇이 달라졌는지
git fetch origin
git range-diff main origin/feature/PAY-256-partial-refund-cancel@{1} origin/feature/PAY-256-partial-refund-cancel
```

브랜치를 아예 받아와서 이어 작업해야 할 땐 다르다. 그건 4번 시나리오다.

```
git switch -c pay-256-review origin/feature/PAY-256-partial-refund-cancel
```

## 왜 지금 이게 필요한가

**리뷰를 받아만 본 사람은 리뷰 요청을 이해하지 못한다.** 5막에서 DEREK 님이 "커밋 좀 나눠주세요"라고 했을 때 IRON은 시키니까 했다. 남의 MR을 6개 커밋으로 읽어보고 나면 그 요청이 잔소리가 아니었다는 걸 안다. **이 시나리오의 절반은 리뷰하는 법이 아니라, 리뷰받는 법을 반대편에서 배우는 것이다.**

기술적으로는 세 가지가 여기서 처음 나온다.

**하나. 점 두 개와 점 세 개.** 리뷰가 아니면 이 구분이 왜 필요한지 설명할 자리가 없다. `git diff main <브랜치>`로 남의 MR을 보면 `main`의 다른 커밋이 통째로 섞여 들어와서 "왜 안 건드린 파일이 지워져 있지"로 헤맨다. 이건 한 번 겪어야 기억에 남는다. 그리고 로그와 디프에서 의미가 뒤집힌다는 사실은 외우는 게 아니라 **"로그는 둘, 디프는 셋"**이라는 규칙으로 잡는 게 실용적이다.

**둘. 디태치드 HEAD의 정당한 용법.** 신입이 이 말을 처음 듣는 자리는 보통 사고 상황이다. 그래서 "빠지면 안 되는 이상한 상태"로 각인된다. 사실 **읽기만 할 거면 가장 깔끔한 방법**이다. 위험한 건 상태가 아니라 거기서 커밋하는 것이라는 걸 여기서 정확히 가른다. 이 구분이 있어야 35번(엉뚱한 브랜치에서 작업함)에서 허둥대지 않는다.

**셋. `range-diff`.** 24번과 25번에서 리뷰 반영 후 강제 푸시를 하게 된다. 그때 리뷰어 쪽에서 무슨 일이 벌어지는지를 지금 보여둬야, 내가 강제 푸시할 때 상대의 부담을 안다.

마지막으로 코멘트 쓰는 법을 명령과 같은 무게로 다룬 이유. **리뷰에서 시간을 잡아먹는 건 Git이 아니라 커뮤니케이션이다.** 줄을 안 찍은 코멘트, 막는 건지 취향인지 모를 코멘트 하나가 왕복 하루를 만든다. 그리고 DEREK 님 대사에 넣은 것 — **좋은 것도 쓴다**. 이건 예의 문제가 아니라, 잘한 방식이 다음에도 반복되게 만드는 가장 싼 방법이다.
