# 36 — 비밀키를 커밋했고 아직 푸시 전이다

> ### 이 시나리오에서 배우는 것
>
> - **배우는 명령** — `git show` · `git log -p -- <파일>` · `git reset --mixed HEAD~1` · `git rm --cached` · `git commit --amend` · `git check-ignore -v` · `git rebase -i` · `git log --all --oneline -- <파일>`
> - **배우는 개념** — 푸시 전이면 히스토리를 조용히 고칠 수 있다. 커밋에서 파일을 빼는 것과 파일을 지우는 것은 다르다. **Git으로 지웠다고 키가 안전해지는 건 아니다.**
> - **끝내면 할 수 있는 일** — 비밀이 커밋에 들어간 걸 발견했을 때 히스토리에서 확실히 빼내고, Git 작업과 별개로 키를 폐기해야 하는지 판단할 수 있다.

## 학습자가 할 일

1. 어느 커밋에 무엇이 들어갔는지 정확히 확인한다 — 파일 이름과 **실제 값**을 본다
2. **Git을 건드리기 전에 알린다.** 폐기가 필요한 키인지 혼자 판단하지 않는다
3. 그 파일이 공용인지 내 것만인지 확인한다
4. 커밋에서 파일을 뺀다. 방법은 둘 중에 고른다 — 커밋을 풀고 다시 하거나, 해당 커밋만 고치거나
5. **로컬 파일은 남아 있어야 한다.** 지운 게 아니라 추적에서 뺀 것이어야 한다
6. `.gitignore`에 규칙을 추가한다. 이번 파일 하나가 아니라 **같은 부류 전체**를 막는다
7. 규칙이 실제로 동작하는지 Git에게 물어 확인한다
8. 히스토리에 그 파일이 남아 있지 않은지 **파일 이름과 키 값 양쪽으로** 확인한다
9. 이제 푸시한다

## 배우는 명령

```
# 1. 뭐가 들어갔는지 확인
git log --oneline -3
git show --stat HEAD~1
git show HEAD~1 -- .env.sandbox
git log --all --oneline -- .env.sandbox         # 이 파일을 건드린 모든 커밋

# 2. 방법 A — 커밋을 풀고 다시 한다 (커밋 수가 적을 때)
git reset --mixed HEAD~2
git status                                      # 파일은 그대로, 커밋만 풀림
git rm --cached .env.sandbox                    # 추적에서만 제거
ls -la .env.sandbox                             # 로컬 파일은 남아 있다

echo ".env*" >> .gitignore
git add .gitignore
git commit -m "chore: .env 파일 전체를 gitignore에 추가"

git add src/payment/GatewayClient.ts src/payment/gateway.config.ts
git commit -m "feat(payment): 게이트웨이 샌드박스 연동 추가

Refs: PAY-279"

# 2. 방법 B — 해당 커밋만 고친다 (커밋이 많을 때)
git rebase -i HEAD~2
# 문제 커밋을 edit으로 표시 → 멈추면
git rm --cached .env.sandbox
git commit --amend --no-edit
git rebase --continue

# 문제가 마지막 커밋이었다면 이것만으로 끝난다
git rm --cached .env.sandbox
git commit --amend --no-edit

# 3. 확인 — 두 가지 방법 모두
git log --all --oneline -- .env.sandbox         # 아무것도 안 나와야 한다
git log -S"sk_sandbox_9f4a2c71e8b350df6a1c" --all --oneline   # 값으로 찾기
git check-ignore -v .env.sandbox                # 규칙이 실제로 잡는지
git status                                      # 파일이 목록에 안 뜨는지

# 4. 이제 푸시
git push -u origin feature/PAY-279-gateway-sandbox
```

이미 푸시했다면 여기서 멈추고 37번으로 간다. 로컬 명령으로 해결되지 않는다.

## 왜 지금 이게 필요한가

**이 시나리오의 절반은 Git이 아니다.**

신입이 이 상황에서 하는 첫 반응은 "빨리 지워야 한다"이고, 그다음이 "아무도 모르게 지워야 한다"이다. 둘 다 위험하다. 앞의 것은 **키 폐기라는 진짜 대응을 건너뛰게** 만들고, 뒤의 것은 팀이 노출 범위를 파악할 기회를 없앤다.

그래서 순서를 명시적으로 뒤집었다. **알리는 게 먼저고 Git이 나중이다.** SAM 님 대사에 "알려줘서 고맙다"를 넣은 것도 의도다. 비밀 노출을 보고하면 혼난다고 믿는 조직에서는 사람들이 숨긴다. 숨긴 사고는 6개월 뒤 훨씬 큰 사고가 된다.

기술적으로 이 자리가 맞는 이유는 세 가지다.

**하나. 푸시 전과 후의 차이가 여기만큼 극적인 곳이 없다.** 푸시 전이면 명령 세 줄이다. 푸시 후면 팀 전체가 재클론하고, 키를 폐기하고, 어디까지 퍼졌는지 조사한다. 8번(커밋 메시지 고치기)에서 "푸시 전이면 공짜, 후면 비용이 붙는다"고 배운 게 여기서 최대치로 회수된다. 이 대비를 한 번 보면 **푸시 전에 `git show`로 훑는 습관**이 왜 값이 있는지 설명이 필요 없어진다.

**둘. "파일을 지운다"와 "추적에서 뺀다"의 구분.** 9번, 10번에서 배운 건데 거기서는 그냥 정리 작업이었다. 여기서는 **틀리면 로컬 개발 환경이 날아간다.** `git rm`과 `git rm --cached`의 차이가 처음으로 실질적인 결과를 만든다.

**셋. 확인하는 법.** 지웠다고 생각하고 푸시했는데 다른 커밋에 남아 있는 경우가 실제로 흔하다. 브랜치를 여러 개 팠거나, 파일 이름을 바꿔가며 여러 번 커밋했거나. 그래서 **파일 이름이 아니라 키 값으로 검색**하는 법을 여기서 가르친다. `git log -S`는 46번에서 다시 나오는데, 첫 등장이 여기인 게 맞다. 여기서는 그게 안전 확인 수단이다.

마지막으로 `.gitignore` 규칙을 **"이번 파일"이 아니라 "같은 부류"**로 쓰게 한 것. 3막에서 `.env.local`을 추가했는데 그게 딱 그 파일 하나만 막았다. 그래서 `.env.sandbox`가 들어왔다. **겪은 것만 막는 ignore는 다음 사고를 못 막는다.** 규칙을 쓸 때 한 칸 넓게 보는 감각을 여기서 잡는다.
