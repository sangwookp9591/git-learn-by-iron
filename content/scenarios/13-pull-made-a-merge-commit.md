# 13 — git pull 했더니 자동으로 머지 커밋이 생겼다

> ### 이 시나리오에서 배우는 것
>
> - **배우는 명령** — `git pull` · `git log --oneline --graph` · `git reset --hard ORIG_HEAD` · `git pull --rebase` · `git pull --ff-only` · `git config pull.ff only`
> - **배우는 개념** — `pull`은 `fetch` + `merge`다. 히스토리가 갈라졌을 때만 머지 커밋이 생긴다. 패스트 포워드와 머지는 같은 명령의 다른 결과다.
> - **끝내면 할 수 있는 일** — 최신 코드를 받기 전에 그냥 받아질지 뭔가 합쳐질지를 미리 판단하고, 원하지 않는 머지 커밋이 생겼을 때 받아온 것을 잃지 않고 되돌릴 수 있다.

## 상황

3일차 아침. 어제 `feature/PAY-231-card-expiry`에서 커밋 두 개를 만들었고 아직 푸시는 안 했다. 자리에 앉아서 늘 하던 대로 `git pull`을 쳤다. 평소처럼 두어 줄 나오고 끝날 줄 알았는데 편집기가 열렸다.

```
Merge branch 'main' of gitlab.dalro.example:payments/dalro-payments

# Please enter a commit message to explain why this merge is necessary,
# especially if it merges an updated upstream into a topic branch.
```

뭔지 모르고 그냥 저장하고 닫았다. 로그를 보니 처음 보는 커밋이 하나 더 있다.

```
*   9c04af1 Merge branch 'main' of gitlab.dalro.example:payments/dalro-payments
|\
| * e7b1d55 refactor(payment): 결제 요청 검증 규칙을 규칙 객체로 분리
| * 1a3f902 fix(refund): 환불 금액 반올림 오류 수정
* | 4d81c6b fix(payment): 만료 카드 요청에 400 반환
* | 7f2a91c feat(payment): 카드 만료일 검증 추가
|/
* b0e5517 chore: CODEOWNERS에 결제팀 추가
```

## 학습자가 할 일

1. `pull` 직후 로그를 그래프로 보고 **머지 커밋이 어디 생겼는지**, 부모가 둘이라는 걸 확인한다
2. 방금 받아온 커밋이 로컬 어디에 남아 있는지 확인한다 (`origin/main`이 가리키는 곳)
3. `pull` 직전 위치로 되돌린다
4. 되돌린 뒤에도 받아온 커밋이 사라지지 않았다는 걸 직접 확인한다
5. 같은 상황을 리베이스 방식으로 다시 처리하고, 커밋 해시가 어떻게 달라졌는지 본다
6. 갈라졌을 때 `pull`이 멈추도록 이 저장소에 설정을 건다
7. 설정을 건 뒤 다시 갈라진 상태를 만들고, `pull`이 실제로 거절하는지 확인한다

## 배우는 명령

```
git log --oneline --graph -10
git log --oneline --graph --all -15
git show --stat 9c04af1                 # 머지 커밋의 부모가 둘인지 확인
git log --oneline origin/main -5        # 받아온 커밋은 여기 남아 있다

git reset --hard ORIG_HEAD              # pull 직전으로
git log --oneline --graph --all -15     # origin/main은 그대로인지 확인

git rebase origin/main                  # 같은 상황을 리베이스로
git log --oneline -5                    # 해시가 바뀐 걸 확인

git config pull.ff only                 # 이 저장소에서만
git pull                                # 갈라져 있으면 거절된다

# 갈라졌을 때 그때그때 고르는 방법
git pull --rebase
git pull --no-rebase                    # 명시적으로 머지
```

되돌아갈 자리를 찾는 다른 방법도 알아둔다.

```
git reflog -10                          # ORIG_HEAD를 못 쓰는 상황일 때
```

## 왜 지금 이게 필요한가

**`git pull`은 신입이 가장 많이 치면서 가장 적게 이해하는 명령이다.** 어제까지 아무 일 없다가 오늘 갑자기 편집기가 뜨는데, 그 차이가 명령이 아니라 **내 상태**에서 왔다는 걸 아무도 안 알려준다. 그래서 "가끔 이상한 게 뜨는 명령"으로 남는다.

여기서 진짜 배우는 건 세 가지다.

**하나. 패스트 포워드와 머지는 같은 명령의 다른 결과다.** 어제와 오늘 같은 명령을 쳤는데 결과가 달랐다. 명령을 바꿔서가 아니라 히스토리가 갈라져서다. 이걸 알면 `pull`을 치기 전에 "지금 갈라져 있나"를 먼저 보게 된다. 그게 14번(`fetch`와 `pull`의 차이)으로 자연스럽게 이어진다.

**둘. 받는 것과 합치는 것은 별개다.** 되돌렸는데 받아온 커밋은 그대로 있다는 걸 눈으로 봐야 이게 몸에 남는다. 그 전까지는 `pull`이 통째로 하나의 동작으로 보인다. 이 구분이 없으면 15번에서 "리베이스하려면 먼저 `fetch`하라"는 말이 왜 나오는지 이해가 안 된다.

**셋. `ORIG_HEAD`가 있다는 것.** 머지·리베이스·리셋 직전 위치가 자동으로 남는다는 걸 알면, 큰 동작을 실행하는 손이 가벼워진다. 되돌릴 수 있다는 사실이 시도의 전제다. 이건 18번의 `--abort`, 40번의 리플로그와 같은 계열의 안전장치다.

그리고 대사에서 일부러 짚은 게 하나 있다. **설정으로 막자는 결론이다.** 사람이 매번 조심하는 것보다 갈라졌을 때 멈추게 해두는 게 확실하다. 9막에서 브랜치 보호 설정 얘기가 나온 것과 같은 결이다.
